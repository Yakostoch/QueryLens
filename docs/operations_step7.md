# Этап 7 — операции плана и сохранение смысла

Патч поверх этапа 6. Новый модуль operation_analysis.py формирует структурированный блок operation_analysis и читаемый раздел отчёта. UI, история и режим EXPLAIN без ANALYZE сохранены; новые зависимости не нужны. Анализ не привязан к схеме bookings или именам контрольных таблиц.

| Правило | Реализовано | Что остаётся неизвестным |
|---|---|---|
| AP06 DISTINCT | Узлы Unique/Aggregate в простой области, входы и стратегия. Для прямой проекции столбцов одной обычной таблицы — доказательство уникальности через валидированный PK и NOT NULL при известном отсутствии наследуемых потомков. | Произвольная уникальность после JOIN, UNIQUE с NULL-семантикой, SRF, сложные выражения, вложенные области. DISTINCT ON сохраняет особый статус. |
| AP07 ORDER BY | Единственный однозначный Sort/Incremental Sort простого запроса, дочерние оценки, ключи, LIMIT. Нет Sort — отдельный статус без вывода о скорости. | Связь сортировок с окнами, DISTINCT и агрегацией; применимость конкретного индекса порядка; измеренный выход на диск. |
| AP09 HAVING | Разбор AND, зависимость от агрегатов, фактическое положение поддержанных условий в Filter/Index Cond относительно агрегации. SQL автоматически не переписывается. |
| AP13 CTE | Число синтаксических потребителей через области SQLGlot; производитель по уникальному Subplan Name, CTE Scan и фильтры по CTE Name. | Исчезновение CTE Scan не доказывает встраивание, Materialize не означает CTE. | AP14 окна | Функции, исходные спецификации, отдельные определения именованных окон, рамки и Run Condition; вход единственного WindowAgg в простой области. | Для нескольких проходов или вложенного SELECT точная привязка не заявляется. Рамка по умолчанию и именованные ссылки не подменяются догадкой; перенос фильтра не считается безопасным. |

Полнота составной связи, допустимость переноса условий, причина дорогого доступа и ошибки оценок требуют дополнительных доказательств/измерения. |

## Данные и ограничения

В нормализованные узлы добавлены Strategy, Group Key, Presorted Key, CTE Name, Join Type, Inner Unique и необязательные измеренные поля сортировки. Без ANALYZE измеренные поля остаются null. В каталоге собирается has_inheritance_children через pg_inherits: PK родителя не гарантирует уникальность всей наследуемой выборки.

Не суммируем стоимости родителя и потомков. Plan Rows дочернего узла является оценкой его выхода, а не точным числом потреблённых строк. Особенно важны LIMIT, параллельный план и повторные обращения. Байты входного потока не объявляются расходом work_mem или прочитанным объёмом.

Поддержка ограничена доказуемыми случаями, а не конкретными именами таблиц. Неизвестные метаданные и сложные области дают явный статус недостаточности данных. Для вложенных SELECT показатели корня не используются. Для CTE с повторённым именем в разных областях привязка по имени не выполняется.

Этот этап не генерирует изменённый SQL: рекомендации описывают условия безопасного эксперимента. Изменение нужных полей, порядка, кратности или рамки окна не применяется автоматически. Фактическое замедление ни одним статусом не подтверждается.

## Проверка

324 автоматических теста: 323 успешны, один native-интеграционный пропущен без отдельной PostgreSQL. В SQL-корпусе 131 пример, включая 22 новых: 128 прошли SQL-планирование/измерение контрольного запроса через PostgreSQL 18.6 в PGlite 0.5.12; три — только синтаксически. Сервис и читаемый отчёт проверены на семи сценариях, включая HAVING, CTE, окна и JOIN.

Отдельно проверены: обычный и DISTINCT ON, обязательное устранение повторов, SRF и наследование, сортировка под LIMIT, порядок индекса, ранний и поздний HAVING, ROLLUP, MATERIALIZED/NOT MATERIALIZED, несколько потребителей CTE, именованные окна, разные проходы, LEFT JOIN и несколько JOIN, другие схемы и quoted identifiers, отсутствие метаданных. Реальный прогон показал ранний отбор user_id=42 при HAVING и отсутствие отдельного Sort для подходящего индексного порядка.

PGlite — SQL-движок PostgreSQL в WebAssembly. Контрольный адаптер не проверяет native psycopg, сетевую авторизацию, macOS или Windows. Эти результаты не доказывают совместимость со всеми версиями PostgreSQL. Для native-проверки предусмотрен scripts/run_sql_lab.py в отдельной локальной базе querylens_test*; изменения откатываются. Приложение по-прежнему использует EXPLAIN без ANALYZE, а измерение выполнялось только отдельным тестовым runner на тестовых данных.

# Этап 5 — SELECT *, OFFSET, COUNT для существования

База: уже установленный QueryLens_joins_step4. Новые зависимости не нужны.
В JSON добавлен volume_analysis. Существующие triage и access_analysis сохранены.
Карточка «Таблицы» переименована в «Объекты БД»: число включает представления.

## SELECT * — AP01

Фиксируются область SELECT, цели звёздочки, раскрытые столбцы и их типы.
Поля берутся из каталоговой привязки и all_fields, без фиксированных имён схем.
Обычный COUNT(*) и имя столбца в кавычках не считаются проекционной звёздочкой.
Для * с USING/NATURAL или производным источником раскрытие не угадывается.
Квалифицированное alias.* простого источника может быть раскрыто отдельно.

Без контракта потребителя вывод consumer_requirements_unknown. Само наличие JSONB,
TEXT, BYTEA или большого plan_width не доказывает лишние поля.
Вложенная звёздочка получает nested_projection_requires_plan_mapping: оптимизатор
может сократить её выход; показатели корня не приписываются вложенному SELECT.

Для прямой простой проекции можно явно передать required_columns. Только тогда
определяется потенциальный избыток полей. Конкретный исправленный SQL для этой
ветви не генерируется. Явное all_output_columns_required=true снимает предложение
сократить состав результата. Ускорение по этим признакам не подтверждается.

## OFFSET — AP08

Фиксируются значение OFFSET и доступный LIMIT, отношение OFFSET/LIMIT при положительном
LIMIT, требуемый размер префикса, ключи порядка и каталоговое доказательство уникальности.
requested_prefix_rows — желаемый префикс потока, не число прочитанных строк таблицы.
Поток может закончиться раньше. Plan Rows ребёнка Limit не считается числом
фактически потреблённых строк. Для LIMIT 0 вводится отдельный статус: строки входа
не требуются; это не обещание полного отсутствия работы планировщика или выражений.

OFFSET 0 не вызывает рекомендации о пропускании. Значения параметров и выражений
не подставляются и не вычисляются предположительно. Для UNION/OFFSET предусмотрен
явный insufficient_data, пока не реализована привязка этой границы к узлу.

Ключи порядка проверяются только в простом источнике по PK либо подходящему
NOT NULL UNIQUE. Учитывается переименование выходных полей: ORDER BY id после
SELECT email AS id не доказывает порядок по первичному ключу id.
Уникальность порядка не доказывает его стабильность при volatile-выражениях или
параллельных изменениях. Курсорная пагинация предлагается условно, без выдуманных
значений курсора и изменения интерфейса навигации.

## COUNT — AP11

Отдельно различаются неизвестное назначение числа, явно нужный точный подсчёт,
порог количества и простая булева проверка. COUNT(column), COUNT DISTINCT и оконный
COUNT не переписываются по правилу COUNT(*). COUNT(*) OVER() относится к окнам.
Вложенные агрегаты не получают показатели корневого узла.

Кандидат EXISTS / NOT EXISTS генерируется только для поддержанных простых булевых
сравнений COUNT(*) с нулём/единицей в единственной проекции одного SELECT и одного
прямого обычного источника. Запрещены для этого правила GROUP BY, HAVING, DISTINCT,
LIMIT/OFFSET, ORDER BY, CTE, вложенные SELECT, окна, FILTER, функции и арифметика.
RLS должен быть явно выключен в полученных метаданных. Если он включён или неизвестен,
источник является представлением либо сведения неполны — кандидат не генерируется.

Кандидат всегда conditional_plain_case и candidate_requires_review=true. Каталоговое
разрешение всех пользовательских операторов и остальных свойств источника ещё не
является формальным доказательством эквивалентности. SQL не применяется и не выполняется
самим приложением. Сохраняется явный alias булева результата, а без alias — стандартное
имя ?column?. Числовой COUNT не заменяется на boolean без изменения контракта.
COUNT(*) > 10, COUNT(*) = 1 и другие количественные пороги сохраняются.

## Контекст потребителя

Сервис получил необязательный keyword-only consumer_context. В обычном окне пока нет
полей его ввода: значения по умолчанию неизвестны. API предназначен для последующего
подключения контракта приложения/формы, не для автоматического угадывания потребностей.
Поддержаны all_output_columns_required, required_columns и count_usage=exact_count /
existence_only. Сырой контекст и посторонние поля не копируются в JSON.

Пример использования на уровне сервиса:

```python
service.analyze(sql, parameters, consumer_context={"required_columns": ["id", "email"]})
```

## Проверки

- 244 автотеста: 243 успешно, один opt-in тест native PostgreSQL пропущен.
- 93 вручную размеченных SQL: 90 выполнены через EXPLAIN ANALYZE BUFFERS в изолированной
  PostgreSQL 18.6 / PGlite 0.5.12 WASM; три параметризованных случая проверены по AST.
- Для четырёх сгенерированных COUNT-кандидатов на тестовой фикстуре совпали значения
  и имена выходных столбцов. Это проверка этих случаев, не доказательство для всех БД.
- Отдельно проверены неизвестные требования к *, явный нужный полный результат,
  USING, алиасы ORDER BY, LIMIT 0, неизвестные параметры, GROUP BY, NULL-семантика
  COUNT(column), FILTER, RLS и функции, для которых переписывание не предлагается.
- Метаданные получены для 89 SQL. Для одного рекурсивного CTE ограничение сборщика
  структуры остаётся явным; сам SQL выполняется и план сохраняется.
- Исправлено разрешение выходного имени в ORDER BY после UNION. При этом сам OFFSET
  этой операции пока остаётся insufficient_data; отсутствие привязки не скрывается.

Тестовый SQL-прогон использует настоящие планы и каталоги через тестовый адаптер
PGlite. Это не покрытие psycopg wire protocol и не бенчмарк native PostgreSQL.
Сравнение скорости до/после и полноценный режим ANALYZE в интерфейсе ещё впереди.

## Воспроизведение

Матрица всех примеров — docs/sql_test_matrix.md и tests/fixtures/sql_cases.json.
Обычная проверка без БД:

```bash
QT_QPA_PLATFORM=offscreen "$HOME/QueryLensEnv/bin/python" -m unittest discover -s tests -v
```

Прогон SQL допускается только в заранее созданной отдельной querylens_test*:

```bash
"$HOME/QueryLensEnv/bin/python" scripts/run_sql_lab.py --database querylens_test_lab --user ИМЯ_РОЛИ
```

Скрипт в этой тестовой базе явно выполняет исходные SQL и доступные SQL-кандидаты
для сравнения результатов. Новые схемы, данные, ANALYZE и опциональный pg_trgm
откатываются общей транзакцией. Не запускайте его в demo или рабочей базе.

Первичные материалы: https://www.postgresql.org/docs/current/functions-subquery.html
и https://www.postgresql.org/docs/current/queries-limit.html.

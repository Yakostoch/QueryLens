# Этап 11: разметка в окне и оценка

## Окно разметки

```bash
python scripts/review_dataset.py --input queue.jsonl --output reviewed.jsonl
```

Исходная очередь не меняется. В существующий reviewed.jsonl можно продолжать
сохранять работу, если он относится к той же очереди. Изменение файла другим
редактором останавливает сохранение, чтобы не затереть чужие правки.

Слева выбирается пример. Справа доступны SQL, черновой ответ и полный контекст.
Ни черновик, ни suggested evidence автоматически не становятся разметкой.
Проверяющий заполняет себя, семью, вывод, ссылки и собственный короткий ответ.

В таблице есть отдельные столбцы:

- «Проверено» → review.assessed_rules: вы действительно проверили это правило.
- «Замечание» → review.labels: по этому правилу есть замечание.

Если правило не проверено, отсутствие метки нельзя считать правильным
отрицательным ответом. Выбор «Замечание» отмечает также «Проверено». Снятие
«Проверено» снимает замечание. Массового одобрения или копирования черновика нет.
Для одобрения в окне нужно хотя бы одно проверенное правило. Черновую работу
можно сохранить со статусом pending и незаполненными полями.

При смене примера и закрытии можно сохранить, отбросить правки или отменить
переход. Некорректное одобрение не сохраняется. На следующем примере одобрение
и ответ предыдущего не подставляются.

## Оценка

```bash
python scripts/dataset_tools.py evaluate reviewed.jsonl --output evaluation.json
```

Без manifest это оценка разработки, а не независимого контроля. Для выбранной
части семейного разделения:

```bash
python scripts/dataset_tools.py split reviewed.jsonl --output-dir training_v1
python scripts/dataset_tools.py evaluate reviewed.jsonl --manifest training_v1/manifest.json --split test --output test_evaluation.json
```

Используйте весь reviewed.jsonl и соответствующий ему manifest. Программа
проверяет распределение семей, идентификаторы и seed. После изменения семей
разделение надо пересобрать; контроль до обучения нужно зафиксировать отдельно.

Сравниваются идентификаторы полезных кратких замечаний с явно проверенными
правилами approved-примеров. problem/potential означают положительную метку;
no_issue_found — отрицательные метки только для assessed_rules.
insufficient_data оценивается отдельно как ожидание отказа от вывода.

Первые три замечания главного экрана и полный набор замечаний отражаются
раздельно. Сам по себе обычный JOIN/Sort/CTE/WindowAgg не становится ошибкой.
Измеренный факт временного I/O не превращается автоматически в AP15 или другую
метку антипаттерна. Метрики не проверяют качество русского текста или LLM.

- Precision = TP / (TP + FP).
- Recall = TP / (TP + FN). Отказ на положительном примере входит в FN.
- F1 = 2TP / (2TP + FP + FN).
- Coverage — доля проверенных решений, где программа дала вывод, а не отказ.
- accuracy_when_answered — правильность среди решений без отказа.
- strict_accuracy — правильность среди всех проверенных решений; отказ не
  засчитывается как правильный ответ.
- strict_case_match — все явно проверенные правила примера совпали без отказов.

При нулевом знаменателе метрика null, а не 100%. Для пустой ручной разметки
status=awaiting_review. Старые approved без assessed_rules не считаются
отрицательными по всем 15 правилам и исключаются с явным счётчиком.

Для оценки правильного отказа при нехватке данных выберите соответствующий
вердикт и проверенные правила. Для подтверждения N+1 по-прежнему нужна трасса
одной операции; loops и частота одного SQL этого не доказывают.

## Ограничения

Это инфраструктура проверки качества, не готовый результат эксперимента. Сами
объяснения по правилам не стали обученной моделью. Нет оснований публиковать
процент правильных причин на неразмеченных 128 записях. Переносимость результатов
тестового стенда на реальные нагрузки также требует отдельной проверки.

Оценка использует сохранённые автоматические проверки и текущий краткий
форматтер; заново SQL не выполняет. После изменения анализаторов нужно заново
собрать их результаты для контроля, а не считать старые записи измерением
качества новой версии правил.

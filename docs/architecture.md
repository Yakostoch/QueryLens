# Разделение интерфейса и логики

```text
main.py собирает WorkspaceController и MainWindow

UI → controllers → services → database / collectors
                 → storage
                 → workers → services
```

Обратная связь в UI приходит сигналами контроллеров. Контроллеры не импортируют
`app.ui`, не получают виджеты и не вызывают методы диалогов.

## Ответственность слоёв

- `ui/`: построение виджетов, чтение полей, сигналы о действиях пользователя,
  навигация, подтверждение замены текста, форматирование и отображение результата.
- `controllers/`: сценарии приложения, состояние, обработка ошибок и время жизни ресурсов.
- `services/`: операции приложения без виджетов; подготовка параметров и анализ.
- `database/`: низкоуровневое соединение с PostgreSQL и будущий исполнитель SQL.
- `storage/`: локальная SQLite-история и настройки. UI не вызывает эти классы.
- `workers/`: выполнение длительных операций в потоке; без доступа к виджетам.

## Контроллеры

`WorkspaceController` объединяет остальные контроллеры, запускает анализ,
решает, сохранять ли результат, и откладывает закрытие до завершения фонового сбора.

`ConnectionController` проверяет подключение, хранит параметры только в памяти,
владеет активным соединением, закрывает тестовое и предыдущее соединения.
Параметры наружу возвращаются копией; сигналы успеха не содержат пароль.

`HistoryController` открывает историю, выполняет поиск/добавление/удаление,
возвращает записи обычными словарями. Ошибка хранения не уничтожает результат анализа.

`SettingsController` выдаёт неизменяемый снимок `SettingsValues`, сохраняет настройки
и сообщает об изменении. Применение темы к виджетам остаётся в UI.

`CollectionController` проверяет возможность запуска, владеет `CollectionWorker`,
не допускает повторный запуск и поддерживает отмену. Соединение сборщика создаётся
и закрывается внутри рабочего потока, отдельно от соединения контроллера подключения.

## Пример: подключение

1. `ConnectionDialog` читает поля и отправляет `connection_requested(parameters, test_only)`.
2. `MainWindow` связывает этот сигнал с `WorkspaceController.connect_database`.
3. `ConnectionController` вызывает `DatabaseService`, тот — `connect_postgresql`.
4. Сигналы `failed`, `tested`, `connected`, `busy_changed` обновляют диалог и окно.

Диалог ничего не знает о драйвере, соединении или проверке допустимости параметров.
Связи с временным диалогом отключаются после его закрытия.

## Пример: анализ

1. Окно получает выделенный SQL или запрос под курсором.
2. Передаёт строку в `WorkspaceController.analyze`.
3. Контроллер запускает `AnalysisWorker`, который вызывает `AnalysisService`.
   Сервис открывает отдельное соединение с параметрами из диалога и через
   `collect_explain` передаёт SQL в `QueryExecutor` как `EXPLAIN (FORMAT JSON)`.
   После ответа контроллер сохраняет результат через `HistoryController`
   с учётом настройки и отправляет `analysis_ready(sql, result, saved)`.
4. Окно показывает результат. История обновляется отдельным сигналом.

`AnalysisService` получает реальный JSON-план без ANALYZE. Рабочее соединение
открывается и закрывается внутри потока анализа; SQL и параметры передаются копией
данных. SQLite-история записывается в потоке контроллера. Без подключения или SQL
задача не запускается. Ошибки не сохраняются в историю. При закрытии приложения
запрашивается прерывание, окно ждёт завершения запроса, ограниченного таймаутом БД.
Повторный запуск и переподключение во время анализа блокируются. Результат для
изменённого во время анализа текста сохраняется в историю, но не подменяет текущий вывод.

Проверка подключения пока синхронная, как до рефакторинга, с таймаутом подключения
из `connection.py`. Её можно перенести в worker без изменения ответственности диалога.

Контроллеры используют `QtCore` для сигналов и потоков, но не `QtWidgets`.
Правила PostgreSQL и анализ в сервисах не зависят от Qt. Форматирование данных для
отображения, подсветка SQL и работа курсора остаются частью интерфейса.

## Сборщики по схеме анализа

```text
SQL / контекст будущего парсера
            ↓
collection_service.collect_features(...)
    ├── explain.collect_explain          → JSON-план
    ├── statements.collect_statements    → pg_stat_statements
    ├── metadata.collect_metadata        → каталоги и статистика всей БД
    ├── configuration.collect_configuration → pg_settings
    └── system.collect_system            → CPU / RAM / Disk
            ↓
sources: статус, исходные структурированные данные, ошибка каждого источника
            ↓
будущий расчёт признаков → QWEN → классификация и рекомендации
```

`collect_features(parameters, sql="SELECT ...", query_id=42)` — новый вход для пяти
источников. `query_id` необязателен: без него сбор статистики запроса пропускается.
Это идентификатор PostgreSQL, не Python-хеш SQL и не результат сравнения текстов.
Отсутствующий SQL аналогично пропускает EXPLAIN. Метаданные пока собираются для
всей базы; фильтрация по таблицам из AST ещё не реализована.

Каждый источник представлен как `{"status": "ok", "data": ..., "error": null}`.
Возможны также `skipped`, `unavailable` (нет расширения) и `error` (ошибка подключения,
прав, запроса или загрузки расширения). Пустой список статистики означает отсутствие
доступной записи, а не нулевое время выполнения. При отмене весь метод возвращает `None`.
Источники собираются последовательно, каждый источник БД использует отдельное соединение:
ошибка транзакции одного сборщика не блокирует остальные. Это не единый снимок БД.

`QueryExecutor` только выполняет запросы на переданном соединении; не создаёт сессию
и не закрывает её. EXPLAIN использует `FORMAT JSON` без `ANALYZE`. Prepared execution
отклоняет несколько SQL-команд в одном вызове. `pg_stat_statements` ищется в схеме
установленного расширения; фильтрация идёт по текущей базе и переданному queryid,
строки разных ролей остаются отдельными. Расширение автоматически не устанавливается.

Источники формата: [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html),
[pg_stat_statements](https://www.postgresql.org/docs/current/pgstatstatements.html),
[Psycopg prepared statements](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html).

Существующий `collect_report()` и адаптер `collectors/postgres.py` сохраняют прежний
формат отчёта для UI. В нём объединяются метаданные и конфигурация. Кнопка
«Анализировать» использует сборщик EXPLAIN; pg_stat_statements пока доступен только
через программный вызов. Парсер, вычисление признаков, QWEN и анализаторы пока
не реализованы. SQL передаётся подключённой локальной PostgreSQL; модель не вызывается.

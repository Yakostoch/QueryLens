# Этап 12: разбор контрольных примеров и конкретные исправления

## Что выполнено

Для всех 50 выбранных случаев подготовлены предложения разметки: ожидаемый
короткий ответ, пояснение, проверяемое направление и ссылки на SQL, план,
метаданные и контракт результата. Это предложения ассистента по исходным
материалам, не независимая человеческая разметка. Все записи остаются pending,
reviewed_by пуст. Никакого процента правильных причин на этом основании нет.

27 предложений имеют no_issue_found, 14 — insufficient_data, 8 — potential,
1 — problem. Последний относится к заведомо ненужным полям при явно заданном
контракте; он не подтверждает фактическую причину задержки. Это распределение
предложенных ответов, не измеренная точность QueryLens.

Семьи assistant_audit_APxx — предварительное укрупнение по направлению. Они
консервативно связывают варианты внутри проверки, но не заменяют сверку семей
со всем будущим обучающим набором. Этот набор не объявляется независимым внешним
бенчмарком или готовым обучающим датасетом.

## Исправления

1. COUNT(столбец) раньше исключался из AP11. Теперь обычные COUNT(выражение)
   участвуют в проверке, а оконные COUNT по-прежнему относятся к AP14. Для
   булевой проверки COUNT(выражение) показывается замечание о NULL и отсутствии
   доказанной безопасной замены; готовый EXISTS автоматически не генерируется.
2. Краткий ответ о коротком LIKE/ILIKE учитывает длину буквального фрагмента.
   Наличие найденного триграммного индекса не превращается в предложение
   создать ещё один; эффективность и применимость требуют проверки.
3. Обычные CTE по-прежнему не объявляются ошибками. Но конкретный случай с
   принудительной материализацией, одним потребителем, сопоставленным
   производителем и фильтром CTE Scan больше не скрывается: пользователь видит
   гипотезу для безопасной проверки фильтра внутри WITH. Автопереноса нет.
4. AnalysisService сохраняет разрешённые поля consumer_context в диагностический
   пакет. Экспорт включает этот вход: теперь известное назначение столбцов или
   точного COUNT можно проверить отдельно от автоматического заключения.

Предыдущие записи не дополняются выдуманными требованиями. При обновлении
тестового корпуса контракты взяты из исходных спецификаций этих сценариев.

## Что выяснилось при разборе

NOT IN на маленьких ненулевых ключах не обязательно требует замены, даже если
NOT EXISTS допустим. OFFSET 10 без LIMIT не является доказательством глубокой
пагинации. Вложенная звёздочка может быть сокращена до id: в одном простом
сохранённом плане это видно вручную, хотя общий анализатор всё ещё воздерживается
от вывода. LATERAL, ROLLUP и несколько окон требуют аккуратного сопоставления.
Эти случаи оставлены в разборе как ограничения и вопросы для проверки, а не
скрыты ради красивой метрики. Для N+1 данных одиночного SQL недостаточно.

## Воспроизводимость

scripts/audit_captured_corpus.py пересчитывает признаки и проверки по уже
сохранённым планам и метаданным. Он не соединяется с БД и не запускает SQL.
Предложения ответов отдельно записаны в tests/fixtures/review_proposals_step12.json.
Они не выводятся автоматически из предсказания самого анализатора и не
переносятся в approved.

Для воспроизведения нужны исходные captures из проверки этапа 7, текущие
tests/fixtures/sql_cases.json и исходный review_plan.json из этапа 11. Утилита
требует новый выходной каталог. Повторная обработка плана не является новым
измерением производительности или тестированием на другой версии PostgreSQL.

## Что делать дальше

вместо заполнения 50 пустых форм. Для положительных примеров отдельно проверить
семантику и доказательства. Одобрять только после проверки. Прежние файлы
пользовательской разметки не перезаписываются; новая очередь имеет новые
идентификаторы из-за изменённых входов и проверок.

Затем зафиксировать семейный контроль, измерить качество и провести повторные
нативные сравнения равнозначных запросов. Модель исключена из текущего объёма работы.
Подготовка предложений разметки не считается обучением LLM или подтверждённым
экспериментом по ускорению SQL.

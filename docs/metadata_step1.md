## Что уже реализовано

Сбор структуры дополнен четырьмя независимыми источниками для каждой выбранной таблицы:

- `indexes`: определения индексов, выражения, условие частичного индекса, порядок ключей,
  INCLUDE, метод доступа, классы операторов, коллации, валидность и признаки уникальности;
- `constraints`: определения ограничений, состав ключей, соответствие столбцов FK,
  проверенность, отложенность и доступные свойства версии сервера;
- `relation`: вид объекта, родители, оценки строк и страниц, размеры самого объекта,
  доступные показатели статистики таблицы и даты ANALYZE;
- `column_statistics`: null_frac, avg_width, n_distinct и correlation с признаком inherited.

У каждого источника есть status/data/error. Ошибка одного источника не отбрасывает
остальные: используются отдельные транзакционные контексты, внутри текущей транзакции —
savepoint. В ошибке сохраняется только имя типа исключения, без текста драйвера.

Успешный пустой список индексов — `ok` и `[]`. Ошибка — `error` и `null`.
Пустая статистика столбцов — `unavailable`: её отсутствие может быть связано с правами,
видом объекта или отсутствием статистики. Причина не придумывается.

В режиме структуры по запросу прежние fields/columns по-прежнему описывают используемые
поля. Новые all_fields/schema_columns сохраняют полную схему источника для раскрытия *.
Новые данные находятся в `tables[].diagnostics.sources`; версия дополненного блока
метаданных — metadata_schema_version=2. Старые ключи отчёта сохранены.

Во вкладке «Анализ БД» текстовый отчёт показывает определения индексов, ограничения,
статус недоступных источников, оценки строк и размеры. Анализатор не утверждает,
что какой-либо индекс применим к конкретному запросу.

Также исправлены два непосредственно связанных дефекта:

1. Фильтр системных схем исключает именно префикс pg_, а не пользовательскую схему
   вроде pgdata из-за wildcard-подчёркивания в LIKE.
2. Вызов qualify больше не передаёт infer_schema, удалённый в SQLGlot 30.24.
   Проверки разрешения имён и неоднозначности проходят с SQLGlot 30.21.0 и 30.24.0.

## Что сделать на своём компьютере

1. Откройте актуальный проект и сохраните свои текущие изменения в git или отдельной копии.
2. Создайте рабочую ветку от своей актуальной версии.
3. Извлеките архив. В нём есть patch и полные версии изменённых файлов в каталоге files.
4. Предпочтительный способ — из корня проекта применить patch:

   `git apply --check /ПУТЬ/QueryLens_metadata_step1.patch`

   Если проверка успешна:

   `git apply /ПУТЬ/QueryLens_metadata_step1.patch`

   Если проверка сообщает конфликт, файлы с тех пор изменились: потребуется слияние,
   а не принудительное применение. Альтернатива — перенести отдельные файлы из files
   по соответствующим путям, предварительно сравнив свои правки. Не заменяйте папку app
   целиком: архив содержит только часть проекта.

5. Используйте действующее виртуальное окружение. Новых зависимостей приложения нет.
6. Из корня проекта выполните:

   `python -m unittest discover -s tests -p 'test_relation_details.py'`

   `python -m unittest discover -s tests -p 'test_query_structure.py'`

   `python -m unittest discover -s tests -p 'test_feature_collection.py'`

7. Запустите приложение своей рабочей командой. Подключитесь к локальной БД.
   На вкладке SQL введите SELECT по существующей учебной таблице. На вкладке «Анализ БД»
   включите сбор структуры, выберите область текущего запроса и нажмите «Собрать показатели».
   В текстовом отчёте появится раздел «Метаданные: схема.таблица».

Не нужно создавать индекс ради этой проверки. Таблица без индексов — корректный случай.
Кнопка «Анализировать» пока по-прежнему показывает обычный EXPLAIN: объединение всех
источников в один анализ и сами правила антипаттернов — следующий этап.

## Проверка изменений

- 21 целевой тест метаданных, разрешения имён и сборщиков проходит с кодом выхода 0.
- Полный набор: 49 тестов, из них 48 пройдены и 1 интеграционный пропущен.
- После сообщения unittest об успехе процесс Qt 6.12.0 в Linux/offscreen завершился
  с SIGSEGV. Та же проблема воспроизведена на исходном main: 39 успешных тестов,
  затем SIGSEGV при завершении процесса. Это не считается полностью чистым GUI-прогоном.
- Четыре каталожных SQL-запроса дополнительно выполнены в PostgreSQL 18.6 через PGlite
  0.5.11. Проверены индекс на выражении, частичный индекс, INCLUDE, DESC/NULLS,
  уникальность NULLS NOT DISTINCT, GIN, составной FK и статистика после ANALYZE.
  PGlite использовался только при разработке; он не является зависимостью QueryLens.
- На обычном сервере PostgreSQL через psycopg интеграционный тест пока не выполнен:
  такой тестовый сервер в среде подготовки не настроен.

## Необязательная проверка на обычном PostgreSQL

Добавлен tests/test_relation_details_postgres.py. Он запускается только при заданной
QUERYLENS_TEST_DATABASE с именем, начинающимся на querylens_test.
Используйте отдельную учебную БД. Тест на loopback создаёт таблицы/индекс в случайной
собственной схеме и удаляет эту схему в конце. Он не должен запускаться на рабочей БД.

Создайте пустую querylens_test_metadata и настройте обычную локальную аутентификацию
PostgreSQL; используются PGUSER/PGPORT и стандартные способы передачи пароля libpq.
Затем в macOS/Linux из корня проекта:

`QUERYLENS_TEST_DATABASE=querylens_test_metadata python -m unittest discover -s tests -p 'test_relation_details_postgres.py' -v`

Пароли не нужно вставлять в исходники или присылать в чат.

## Ограничения этого шага

Сборщик читает каталоги и статистику; пользовательский SELECT ради получения этих
метаданных не выполняется. Размеры относятся к самому объекту без рекурсивной суммы
секций. Отсутствующие свойства старой версии сервера сохраняются как null.
Оценки не превращаются в фактическое количество строк, n_distinct сохраняет исходный
смысл PostgreSQL. Проверки применимости индекса, доказательства эквивалентности,
свойства функций, полная поддержка представлений/секций и связь с планом ещё впереди.

Первое продолжение: собрать SQL-признаки и расширенный оценочный план, связать их с
этими метаданными и реализовать AP02/AP03 как проверки кандидатов с явными ограничениями.

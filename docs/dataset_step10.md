# Локальный датасет QueryLens: часть 2 этапа 10

## Что готово

Кнопка «В датасет» сохраняет текущий анализ в JSONL. Для этого не нужны история
или повторный запуск SQL. Она доступна и для подходящих записей истории.
После изменения SQL, ошибки или отмены сохранение старого анализа отключается.

Парсер `scripts/dataset_tools.py` читает сохранённые текстовые отчёты с JSON,
отдельные диагностические JSON-пакеты и SQLite-историю QueryLens. История
открывается только для чтения, без ограничения последними 200 записями интерфейса.
Точные повторения объединяются; старые отчёты без дерева пропускаются с сообщением.
Это не универсальный парсер любых публичных SQL-датасетов: для нового формата
нужен отдельный адаптер и проверка лицензии. План нельзя восстановить из одного
SQL без соответствующей схемы и среды PostgreSQL.

## Состав записи

| Поле | Содержание |
|---|---|
| case_id | Хеш исходных входов и автоматических проверок; не queryid PostgreSQL |
| query_fingerprint | Форма SQL без значений литералов для объединения похожих запусков |
| provenance | Идентификатор и время анализа, режим и происхождение |
| input | SQL, исходный EXPLAIN, метаданные, настройки и доступные признаки |
| automatic_analysis | Проверки 15 конструкций и дерево; автоматически полученные свидетельства |
| draft_answer | Текущий краткий ответ; черновик, не эталон |
| review | Ручная разметка; изначально pending, ответ и метки пусты |

Данные остаются в выбранных локальных файлах. Параметры подключения не являются
полями экспорта. При этом SQL, план и статистика могут содержать чувствительные
литералы, названия и значения: автоматической анонимизации нет. Не публикуйте
рабочие диагностические записи без отдельной проверки содержимого.

Настройки диагностической сессии PostgreSQL входят в sources.configuration.
Метрики компьютера с вкладки «Ресурсы» не синхронизированы с выполнением SQL,
поэтому не подставляются в запись как доказательство нагрузки сервера БД.

## Ручная проверка

Создайте отдельный лист разметки, чтобы не редактировать большие планы:

```bash
python scripts/dataset_tools.py review-sheet review_queue.jsonl --output review_sheet.json
```

Для каждого примера в `items` заполните `review`:

- `status`: pending (ещё не проверен), rejected (исключён) или approved (проверен).
- `reviewed_by`: идентификатор проверяющего.
- `family_id`: общая группа для исходного запроса, исправления, других объёмов
  данных, схем и значений параметров одного сценария.
- `verdict`: problem, potential, no_issue_found или insufficient_data.
- `labels`: список идентификаторов AP01–AP15; для хорошего запроса допустим `[]`.
- `evidence_refs`: JSON Pointer в исходную запись, например `/input/sql` или
  `/automatic_analysis/operation_analysis/findings/0`. Для problem/potential
  нужны метки и разрешаемые ссылки. Подсказки `evidence_suggestions` не заменяют
  проверку достаточности доказательств.
- `answer`: проверенный короткий ответ обычному пользователю: где замечание,
  почему, что сделать. Если данных недостаточно, это должно быть сказано явно.
- `notes`: комментарий проверяющего; в обучающий запрос он не передаётся.

Не подтверждайте фактическое замедление по одному наличию конструкции или cost.
Для сравнений времени нужны повторные измерения равнозначных вариантов в
сопоставимых условиях. Даже approved означает ручную проверку, а не автоматическое
доказательство правильности. Программа проверяет структуру разметки, но не может
заменить эксперта при проверке смысла SQL и обоснованности причинного вывода.

Исходный SQL в листе приведён для удобства: его правка не меняет исходные записи.
Для нового SQL нужен новый анализ и запись. Поле `draft_answer` нельзя автоматически
переносить в answer с массовым approved без проверки.

```bash
python scripts/dataset_tools.py apply-review review_queue.jsonl review_sheet.json --output reviewed.jsonl
python scripts/dataset_tools.py split reviewed.jsonl --output-dir training_v1
```

Команды не перезаписывают существующие выходные файлы. `split` создаёт
train.jsonl, validation.jsonl, test.jsonl и manifest.json только при наличии
пригодных approved. Пример без ручного ответа или семьи не проходит проверку.
Остальные pending/rejected не попадают в обучающие файлы.

## Защита разделения данных

Одна семья и одинаковая форма SQL всегда остаются в одной части. Группировка
транзитивна: если две семьи пересекаются по форме SQL, они объединяются.
Разделение детерминировано для фиксированных записей и seed, ориентир 80/10/10.
На маленьком наборе некоторые части могут быть пустыми; это отражается в manifest.
После изменения состава групп разделение нужно сформировать и проверить заново.

Общий family_id для равнозначных переписываний и вариантов схем задаёт человек.
Fingerprint не доказывает семантическую эквивалентность и не находит все варианты
утечки. Не заменяйте ручные семьи независимым случайным разделением строк.

В messages передаются входы и автоматические свидетельства. draft_answer, ручные
метки и заметки не являются входом модели; assistant содержит только ручной answer.
Это формат для будущего дообучения объясняющей модели, а не независимая оценка
обнаружения антипаттернов: автоматическое дерево уже содержит их идентификаторы.
Для проверки классификации правил нужна отдельная оценка по ручной разметке.

## Дальше

Готовые технические записи корпуса ещё не являются размеченным обучающим набором.
Сначала проверить положительные, хорошие, сложные и недостаточные случаи, включая
NULL, дубликаты, CTE, окна, разные схемы, права и индексы. Для N+1 необходима трасса
одной операции приложения; одиночного SQL недостаточно. Не подменять её loops.

После разметки зафиксировать независимый контрольный набор, измерить точность
правил и качество ответов. Подключение модели исключено из текущей версии;
для работы приложения разметка и обучение не требуются.

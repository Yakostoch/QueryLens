# Этап 2: диагностический контекст и маршрутизация

База: main d09f5e3 с применённым этапом metadata_step1. Существующие окна, вкладки,
контроллеры и формат строкового сигнала результата сохранены.

## Что выполняется

1. SQLGlot разбирает один SELECT, включая допустимые CTE и операции над наборами.
   Проверка SQL — ограничение поддерживаемого входа, не полноценная песочница.
2. Из исходного AST извлекаются конструкции до раскрытия звёздочек.
3. EXPLAIN (VERBOSE, FORMAT JSON) сохраняется полностью, без ANALYZE.
4. Дерево плана разворачивается в узлы с путями и связями с родителями.
5. В том же соединении независимо собираются настройки и метаданные запроса.
   Отказ необязательного источника не скрывает уже полученный план.
6. В метаданные добавляются отношения из плана. Например, aircrafts и
   aircrafts_data сохраняются отдельно: индексы базовой таблицы не приписываются представлению.
7. Все 15 сценариев получают постоянные идентификаторы и статусы предварительного отбора.
8. В существующее окно анализа возвращаются краткий текст и полный JSON-контекст.

## Группы дерева

| Группа | Сценарии |
| --- | --- |
| Объём и лишняя работа | AP01 SELECT *, AP08 OFFSET, AP11 COUNT для существования |
| Доступ и фильтрация | AP02 выражение над столбцом WHERE, AP03 начальный %, AP04 OR |
| Кратность и соединения | AP06 DISTINCT, AP12 декартово произведение, AP15 JOIN |
| Сортировка и обработка групп | AP07 сортировка, AP09 HAVING, AP14 окна |
| Промежуточные результаты | AP05 NOT IN с подзапросом, AP13 CTE |
| Вызовы приложения | AP10 N+1 |

Группы могут активироваться одновременно. Это предварительная маршрутизация:
наличие COUNT, JOIN, DISTINCT или CTE не считается доказанной проблемой.

## Контракт JSON

schema_version, analysis_id, started_at, finished_at, mode, sql, sql_features,
plan_summary, plan_features, explain, sources.metadata, sources.configuration, triage.

Каждый узел содержит собственные оценки; estimated_bytes — произведение выходных
Plan Rows и Plan Width. Неизвестные значения сохраняются как null. Total Cost не
переводится в миллисекунды. Накопленные показатели всей БД не выдаются за метрики SQL.
Даты сериализуются ISO 8601, Decimal — строкой без потери точности.

Каждая запись triage содержит rule_id, group, name, status, syntax_matches,
cause_assessment, missing_evidence, recommendation_status.
Статусы: candidate / no_syntax_candidate / insufficient_data.
cause_assessment остаётся not_evaluated, recommendation_status — not_generated.

## Границы этапа

Применимость индекса и точная связь предиката SQL с выражением плана ещё не определяются.
Нет подтверждённых диагнозов, ранжирования причин, исправленного SQL или обучения LLM.
N+1 требует трассы операции приложения. SELECT * требует контракта нужных полей.
Для COUNT требуется назначение результата. Ресурсы ОС остаются отдельным измерением
клиентского компьютера, без временной привязки к запросу и без предположения о сервере.

EXPLAIN без ANALYZE не измеряет выполнение SQL. Функции, вызываемые на стадии
планирования, и сам планировщик всё же могут выполнять работу. Индексы, настройки,
данные и статистика автоматически не изменяются.

## Проверка

85 тестов: 84 успешно, 1 пропущен. Проверены AST, шаблоны с ESCAPE и неизвестными
параметрами, нормализация плана, независимость источников, представления и базовые
таблицы, интерфейс, контроллеры и история. Пропущен opt-in тест с настоящим PostgreSQL.
Локальная среда: PySide6 6.8.3, SQLGlot 30.25.0. Проверка на вашей БД — отдельный шаг.

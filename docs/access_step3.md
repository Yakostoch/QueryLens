# Этап 3: AP02/AP03 и контрольный набор SQL

База патча: актуальная main d09f5e3 с уже установленными metadata_step1 и analysis_step2.
Внешний вид, вкладки, контроллеры, история и строковый сигнал результата сохранены.

## Реализовано

- Структурное сопоставление сравнения SQL с Filter / Index Cond / Recheck Cond.
  SQLGlot понимает серверные операторы ~~ и ~~* как LIKE и ILIKE.
- Учёт псевдонима таблицы и типа столбца при ограниченной нормализации text-приведений.
  Произвольные числовые/временные приведения не удаляются.
- Проверка ключей индексов: выражения, исходные столбцы, позиции, pg_trgm,
  частичные предикаты, ready/valid/live. INCLUDE не считается поисковым ключом.
- Индекс по совпадающему выражению считается кандидатом. Только наличие данного
  предиката в Index Cond соответствующего индексного узла отмечается как наблюдаемый доступ.
  Наличие индекса само по себе не доказывает его применимость или полезность.
- Bitmap Index Scan сопоставляется только внутри уже определённого Bitmap Heap Scan.
- Маленькая оценочная таблица не получает автоматический совет создать индекс.
  1000 строк — явная эвристика контекста, не порог замедления и не доказательство дешевизны.
- Для больших источников с фильтрацией выдаются условные направления проверки,
  без исправленного SQL, автоматического DDL или обещания ускорения.
- COUNT(*) OVER() исключён из кандидатов COUNT для существования: это оконное вычисление.

## Ограничения

Поддержано достоверное сопоставление для одного прямого SELECT обычной таблицы
или материализованного представления с простыми сравнениями и AND. JOIN, CTE,
несколько SELECT, OR/NOT, обычные представления, секционированные родители,
неизвестные типы и неоднозначные/преобразованные предикаты возвращают unknown.
Это ограничение автоматической привязки, а не запрет на получение исходного плана.

Обычный EXPLAIN не подтверждает фактическое замедление. Slowdown_confirmed остаётся false:
это означает отсутствие подтверждения, а не доказанную оптимальность запроса.
Проверка применимости частичного индекса, collation, перегруженных операторов,
преобразований планировщика и стоимости не заменяется совпадением текста.
Ресурсы ОС пока собираются отдельно, без приписывания нагрузки одному SQL.
LLM и генерация обучающих меток не добавлены.

## Дерево результата

Конструкция AP02/AP03 → разрешимый прямой источник? → сравнение однозначно?
→ соответствует условию конкретного узла? → есть Index Cond для него?
→ если нет: контекст размера и кандидаты индексов → условная рекомендация.
Любая недоказанная связь приводит к unknown и указанию недостающих сведений.
Несколько групп могут быть активны в одном запросе.

В JSON добавлен access_analysis с findings: binding_status, predicate_expression,
relation, predicate_plan_roles, plan_evidence, node_metrics, table_estimated_rows,
base_column_index_exists, base_column_indexes, index_metadata_status,
index_candidates, risk_assessment, recommendations, slowdown_confirmed.
Синтаксический triage всех 15 сценариев сохранён отдельно от этого анализа.

## Проверки

- 178 автоматических тестов: 177 успешно, 1 opt-in тест native PostgreSQL пропущен.
- 68 вручную размеченных SQL: 16 потенциально проблемных, 14 допустимых конструкций,
  16 хороших контрольных, 15 сложных, 3 граничных, 4 с недостаточными данными.
- Не менее четырёх примеров на каждый из 15 сценариев.
- 66 запросов получили EXPLAIN и были выполнены через EXPLAIN ANALYZE BUFFERS в
  изолированной тестовой схеме; два параметризованных случая проверены синтаксически.
- SQL-движок проверки: PostgreSQL 18.6 в PGlite 0.5.12 (WASM). Настоящие планы и каталоги,
  тестовый адаптер соединения; psycopg wire protocol и Homebrew PostgreSQL этой проверкой
  не покрыты. Это отдельная проверка от unit/GUI-тестов.
- Метаданные доступны для 65 исполняемых примеров; один рекурсивный CTE ожидаемо
  даёт QueryStructureError в сборщике структуры, сохраняя план и SQL-выполнение.
- Подтверждены реальные примеры Index Scan по lower(name) и Bitmap Heap/Index Scan
  по gin_trgm_ops. Их планы сохранены как регрессионные фикстуры.
- Полный сервис формирования отчёта проверен на этих двух примерах.

Результаты не являются оценкой точности диагностики всех 15 причин: AP04–AP15 пока
в основном имеют синтаксическую маршрутизацию. N+1 по одному SQL остаётся непроверяемым.
Нужные столбцы SELECT * и назначение COUNT требуют контекста потребителя.
Время WASM-прогона не является бенчмарком скорости PostgreSQL на компьютере пользователя.

## Воспроизведение

Без подключения к БД:

```bash
QT_QPA_PLATFORM=offscreen "$HOME/QueryLensEnv/bin/python" -m unittest discover -s tests -v
```

Все SQL и ожидаемые кандидаты: docs/sql_test_matrix.md и tests/fixtures/sql_cases.json.

Для отдельной локальной тестовой БД querylens_test* (НЕ demo):

```bash
"$HOME/QueryLensEnv/bin/python" scripts/run_sql_lab.py --database querylens_test_lab --user ИМЯ_РОЛИ
```

База должна быть создана заранее; скрипт её не создаёт и не удаляет.
Роли нужны права создания схемы и таблиц в этой тестовой БД. Пароль можно задать
обычным механизмом PostgreSQL (.pgpass / PGPASSWORD); отчёт его не содержит.
Скрипт создаёт новую схему querylens_lab и отказывается переиспользовать существующую.
DDL, данные, ANALYZE и измерения откатываются общей транзакцией. Сторонняя схема не удаляется.
С --with-trigram требуется доступное расширение pg_trgm; его создание и тестовый GIN
индекс тоже откатываются. Не запускайте fixture SQL отдельно в рабочей базе.
Отчёт сохраняется в sql_lab_results.json. Один запуск — проверка работоспособности,
не сравнительный эксперимент ускорения. Приложение по-прежнему выполняет EXPLAIN без ANALYZE;
фактическое выполнение в этом этапе предусмотрено только отдельным тестовым скриптом.

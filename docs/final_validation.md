# Завершение проверки QueryLens

Окно разметки пока можно закрыть. Проверка 50 предложений ИИ не является условием запуска приложения и сама по себе не доказывает качество диагностики.

## Сейчас: два измеряемых примера

Запустите из папки приложения:

```bash
"$HOME/QueryLensEnv/bin/python" scripts/finish_check.py --execute
```

Введите название локальной базы (по умолчанию demo), роль PostgreSQL и пароль. Пароль не отображается и не сохраняется в отчёт. Пустой пароль позволяет использовать .pgpass или подключение без пароля, если это настроено на сервере.

Для демонстрационной базы bookings проверяются две пары:

1. `SELECT DISTINCT flight_id FROM bookings.flights` и тот же запрос без DISTINCT. В известной схеме flight_id — первичный ключ. Для другой схемы это нужно проверить заново.
2. `COUNT(*) > 0` и EXISTS по условию flight_id = 1 в ticket_flights. Оба варианта возвращают булево поле has_tickets. Даже отсутствие совпадений является корректным случаем; ускорение не гарантируется.

Сначала PostgreSQL проверяет имена и типы полей, затем равенство наборов с учётом повторов и NULL в одной транзакции REPEATABLE READ. Порядок строк не проверяется. При различиях замеры не запускаются. При успехе выполняются пять замеров каждого варианта с чередованием порядка. Ограничение каждого SQL — 5 секунд.

Появится новая папка QueryLens_results_ДАТА_ВРЕМЯ на рабочем столе. Откройте RESULTS.txt: там короткий итог. distinct.json и exists.json содержат планы и отдельные замеры. Отчёты содержат SQL и названия объектов, но не пароль подключения.

Проверка равенства относится к текущим данным, а не доказывает эквивалентность для всех возможных данных. Проверяются имена и OID типов, а не все свойства контракта приложения. Времена измеряются после проверки, которая могла прогреть кеш. Нагрузка и изменения данных между соединениями не изолированы. При тайм-ауте или ошибке завершённый результат не выдумывается.

## Своя база PostgreSQL

Сервис не использует имена bookings: они есть только в двух стартовых примерах. Для своей схемы подготовьте два вручную проверенных SELECT в файлах и запустите:

```bash
"$HOME/QueryLensEnv/bin/python" scripts/finish_check.py --execute --original before.sql --candidate after.sql
```

Используйте детерминированные запросы, где порядок результата не является частью контракта. Случайные значения, последовательности, функции с внешними эффектами и запросы с нестабильной пагинацией для этой проверки не подходят. Нормализованные SQL сохраняются в отчёт и используются как для сравнения результатов, так и для замеров. Подключение использует существующий режим приложения: локальная PostgreSQL через 127.0.0.1, порт по умолчанию 5432; другой порт задаётся --port.

## Что остаётся до сдачи

1. Получить реальные отчёты этих двух сравнений на целевой PostgreSQL. Один ручной замер 19.9 против 14.7 мс не заменяет повторную проверку.
2. Завершить проверку всех 15 правил на положительных, хороших и сложных SQL из тестового набора; отдельно проверить недостаток прав, представления, другие схемы, NULL, составные ключи и отмену. Два сравнения выше не заменяют эту проверку. Фиксировать и пропуски, и ложные предупреждения.
3. Проверить установку и GUI на целевых macOS и Windows. Указать фактически проверенные версии PostgreSQL; обещание работы с любой схемой не означает уже проверенную совместимость со всеми версиями.
4. В документации описать архитектуру, границы анализа, реальные измерения и воспроизводимый запуск. Настройки компьютера клиента не выдавать за ресурсы сервера PostgreSQL.

Автоматические тесты и проверка SQL в PGlite полезны для разработки, но не заменяют запуск на установленной PostgreSQL пользователя. Проект нельзя объявлять полностью проверенным до завершения целевых проверок.
